Quick guide

Wanted outputFrom Linux AMD64 runnerRecommended method
Linux AMD64 binaryYesNative compiler installed by the job.
Linux ARM64 binaryYesCross-compiler such as aarch64-linux-gnu-gcc.
Docker linux/amd64YesDocker Buildx.
Docker linux/arm64YesBuildx + QEMU/binfmt.

The Neko runner image is intentionally lightweight. Heavy SDKs and compilers are not permanently baked into it. Install the tools a workflow needs, or build a reusable builder image for repeated jobs.

Runner labels

Route Docker-capable jobs to the self-hosted runner with labels. The actual machine still has its GitHub default architecture label such as X64 or ARM64.

jobs:
  build:
    runs-on:
      - self-hosted
      - Linux
      - docker
      - buildx

Use X64 when the job itself must execute natively on AMD64. Do not add ARM64 just because the job produces an ARM64 Docker image; an AMD64 node can cross-build that image with Buildx/QEMU.

Build a Linux AMD64 binary

For a native C/C++ build on an AMD64 node, install only the compiler packages needed by that job.

name: Linux AMD64 binary

on:
  push:
  workflow_dispatch:

jobs:
  build:
    runs-on: [self-hosted, Linux, X64]
    timeout-minutes: 60

    steps:
      - uses: actions/checkout@v4

      - name: Install compiler
        run: |
          sudo apt-get update
          sudo apt-get install -y --no-install-recommends build-essential

      - name: Build
        run: |
          mkdir -p dist
          gcc -O2 -o dist/myapp-linux-amd64 src/main.c
          file dist/myapp-linux-amd64

      - uses: actions/upload-artifact@v4
        with:
          name: myapp-linux-amd64
          path: dist/myapp-linux-amd64

Build a Linux ARM64 binary on AMD64

For C/C++, a cross-compiler is normally much faster than emulating a complete ARM64 machine.

name: Linux ARM64 binary from AMD64

on:
  push:
  workflow_dispatch:

jobs:
  build-arm64:
    runs-on: [self-hosted, Linux, X64]
    timeout-minutes: 60

    steps:
      - uses: actions/checkout@v4

      - name: Install ARM64 cross compiler
        run: |
          sudo apt-get update
          sudo apt-get install -y --no-install-recommends \
            gcc-aarch64-linux-gnu \
            g++-aarch64-linux-gnu

      - name: Cross compile
        run: |
          mkdir -p dist
          aarch64-linux-gnu-gcc -O2 \
            -o dist/myapp-linux-arm64 src/main.c
          file dist/myapp-linux-arm64

      - uses: actions/upload-artifact@v4
        with:
          name: myapp-linux-arm64
          path: dist/myapp-linux-arm64
For Go, Rust, Zig and other languages, prefer their native cross-target support when possible instead of CPU emulation.

Build and push AMD64 + ARM64 Docker images

This is the main multi-architecture setup for the runner. An AMD64 VPS can build and publish ARM64 images at any time.

name: Multi-arch Docker image

on:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read
  packages: write

jobs:
  docker:
    runs-on: [self-hosted, Linux, docker, buildx]
    timeout-minutes: 120

    steps:
      - uses: actions/checkout@v4

      - name: Set up QEMU
        uses: docker/setup-qemu-action@v3
        with:
          platforms: arm64,amd64

      - name: Set up Buildx
        uses: docker/setup-buildx-action@v3

      - name: Log in to GHCR
        uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and push
        uses: docker/build-push-action@v6
        with:
          context: .
          platforms: linux/amd64,linux/arm64
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:latest
            ghcr.io/${{ github.repository }}:sha-${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
Your node also registers multi-architecture binfmt support at startup when ENABLE_MULTIARCH_ON_START=true. Keeping setup-qemu-action in a workflow is still a useful self-contained safety check.

Build ARM64 only

- uses: docker/setup-qemu-action@v3
  with:
    platforms: arm64

- uses: docker/setup-buildx-action@v3

- uses: docker/build-push-action@v6
  with:
    context: .
    platforms: linux/arm64
    push: true
    tags: ghcr.io/YOUR_ORG/YOUR_IMAGE:arm64

Build Windows C/C++ files from Linux

MinGW-w64 can create Windows PE .exe and .dll files while the job itself runs on Linux.

name: Windows x64 EXE from Linux

on:
  push:
  workflow_dispatch:

jobs:
  windows-cross:
    runs-on: [self-hosted, Linux, X64]
    timeout-minutes: 60

    steps:
      - uses: actions/checkout@v4

      - name: Install MinGW-w64
        run: |
          sudo apt-get update
          sudo apt-get install -y --no-install-recommends mingw-w64

      - name: Build Windows x64 EXE
        run: |
          mkdir -p dist
          x86_64-w64-mingw32-gcc -O2 \
            -o dist/myapp-windows-x64.exe src/main.c
          file dist/myapp-windows-x64.exe

      - uses: actions/upload-artifact@v4
        with:
          name: myapp-windows-x64
          path: dist/myapp-windows-x64.exe

For a 32-bit Windows binary, use i686-w64-mingw32-gcc. For C++, use the corresponding g++ compiler.

A MinGW-built Windows binary is not an MSVC build. If your project requires Visual Studio project tooling, MSVC libraries, signing tools only available on Windows, COM registration, or Windows SDK behavior that MinGW cannot provide, use a Windows runner.

Build Windows .NET from Linux

.NET supports cross-targeted publishing from Linux. The SDK can be installed for the job with the official setup action.

name: Windows .NET from Linux

on:
  push:
  workflow_dispatch:

jobs:
  windows-dotnet:
    runs-on: [self-hosted, Linux, X64]
    timeout-minutes: 60

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-dotnet@v4
        with:
          dotnet-version: '8.0.x'

      - name: Publish Windows x64
        run: |
          dotnet restore
          dotnet publish -c Release \
            -r win-x64 \
            --self-contained true \
            -o dist/win-x64

      - uses: actions/upload-artifact@v4
        with:
          name: windows-x64
          path: dist/win-x64/

Change the RID to win-arm64 when the project and dependencies support Windows ARM64.

Keep binaries as GitHub artifacts

If you are producing files rather than container images, upload them so they are available from the workflow run.

- name: Upload build output
  uses: actions/upload-artifact@v4
  with:
    name: release-files
    path: dist/
    if-no-files-found: error
    retention-days: 14

One workflow for several binary targets

This example builds three C targets on one Linux AMD64 runner. Matrix jobs may run in parallel only when you have enough separate runner instances; one runner process accepts one job at a time.

name: Cross-platform binaries

on:
  workflow_dispatch:
  push:

jobs:
  build:
    runs-on: [self-hosted, Linux, X64]
    timeout-minutes: 60
    strategy:
      fail-fast: false
      matrix:
        target: [linux-amd64, linux-arm64, windows-x64]

    steps:
      - uses: actions/checkout@v4

      - name: Install toolchain
        run: |
          sudo apt-get update
          case "${{ matrix.target }}" in
            linux-amd64)
              sudo apt-get install -y --no-install-recommends build-essential
              ;;
            linux-arm64)
              sudo apt-get install -y --no-install-recommends gcc-aarch64-linux-gnu
              ;;
            windows-x64)
              sudo apt-get install -y --no-install-recommends mingw-w64
              ;;
          esac

      - name: Build
        run: |
          mkdir -p dist
          case "${{ matrix.target }}" in
            linux-amd64)
              gcc -O2 -o dist/myapp-linux-amd64 src/main.c
              ;;
            linux-arm64)
              aarch64-linux-gnu-gcc -O2 -o dist/myapp-linux-arm64 src/main.c
              ;;
            windows-x64)
              x86_64-w64-mingw32-gcc -O2 -o dist/myapp-windows-x64.exe src/main.c
              ;;
          esac

      - uses: actions/upload-artifact@v4
        with:
          name: ${{ matrix.target }}
          path: dist/

What Linux cannot replace

TaskLinux runner?Reason
MinGW Windows EXE/DLLYesCross-compilation is supported.
.NET win-x64 / win-arm64 publishUsuallyModern .NET supports cross-RID publishing.
MSVC cl.exeNoRequires Microsoft Windows toolchain/runtime environment.
Visual Studio solution requiring VS workloadsNoUse a Windows self-hosted or GitHub-hosted Windows runner.
Windows Docker containersNoA Linux Docker daemon cannot run Windows containers.
Native Windows integration testsNoThe produced executable needs Windows to execute normally.

Tips for a slow VPS

  • Prefer a cross-compiler for ARM64 binaries instead of full QEMU emulation.
  • Use Buildx cache for Docker builds: cache-from: type=gha and cache-to: type=gha,mode=max.
  • Only install build packages in jobs that need them.
  • If the same large SDK is installed every build, create a small dedicated builder image and use it repeatedly.
  • Set a sensible timeout-minutes so an impossible build does not occupy a node forever.
  • The dashboard/node-agent cleanup system can remove unused Buildx cache and images after a job finishes.
  • Do not route an ARM64-output Docker job exclusively to an ARM64 physical node unless you specifically need native ARM64 execution. AMD64 → ARM64 Docker cross-build is supported.
Rule of thumb: use native execution when you need to run/test the target program, and use cross-compilation or Buildx when you only need to produce the target output.
